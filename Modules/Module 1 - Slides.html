Frame

Every Product Manager is now
an AI Product Manager

Whether managing infrastructure, UI, or core features, you are now managing outcomes.

In 2023, “AI PM” meant you built a chatbot or a wrapper. Today the bar is higher. Software has moved from deterministic to probabilistic. Even if you don’t think you build AI, your competitors do, and your users now expect personalisation, speed, and intuition. You are managing systems that can surprise you. That changes how you spec, test, and ship. That changes everything.

Speaker Notes

The big frame. AI is no longer a vertical specialty — it's baseline competency for every PM. Like mobile in 2015. Every PM needs AI fluency now.

Mental Model

From Rules to Probabilities

Deterministic vs. Non-Deterministic Systems — the single biggest mental model shift.
Deterministic Systems

Most software you’ve managed. The code follows rigid pre-written instructions where the same input always produces the exact same output.

E.g. keyword search, login auth, Excel formulas.

VS
Probabilistic Systems

AI-powered products. The model predicts the most likely next step, where the same input can produce different valid outputs each time.

E.g. semantic (RAG) search, LLM summarisation, image generation.

You can no longer write “the output will be X.” You define the qualities and guardrails of an acceptable output.

Speaker Notes

The single biggest mental model shift for a PM in this era: deterministic to probabilistic. Drive home: same input can produce different valid outputs. Acceptance criteria can't say 'output will be X' anymore — they specify qualities and guardrails.

Operating Mode

Navigating Uncertainty:
The PM’s Dual Role

Same job. Two operating contexts. Different skills.
🏗️
When Building AI Products

When scoping requirements for stakeholders and engineering, you can’t define a single exact output — the system is designed to change.

Your PRD must evolve to specify qualities and guardrails of an acceptable response — ensuring the team builds a safe, reliable AI experience. You’re a city planner, not a building architect.

AI uncertainty
⚡
When Using AI in Workflows

The AI’s variability can be a source of creativity — but it means you are responsible for critically evaluating each unique output.

You guide the AI toward the desired result through prompt iteration and your strategic judgment. The interaction is a conversation, not a command.

Your job is to guide AI toward the desired result by iterating on your prompts and applying your strategic judgment.

Speaker Notes

PM operates in two modes. Building AI Products: city planner (zoning laws, not buildings). Using AI in Workflows: conversation, not command — judgment lives in iteration.

Framework

How the AI-Era PM Role Has Evolved

PMs must move from defining deterministic specs to owning the outcomes of probabilistic systems.
1
Assess the AI-Ability of the Problem

Validate if the problem truly needs a probabilistic solution. Avoid using AI where a deterministic rule delivers better predictability and value.

2
Own the “Vibe” & Trade-offs

Configure the specific balance of cost, latency, and quality. Define the model's behaviour through parameters — not abstract concepts.

3
Define the Failure State

Design explicitly for variability. Create guardrails, feedback loops, and fallback UIs to maintain trust when the AI inevitably fails.

4
Prototype as Spec

Replace static requirements with functioning prompts. Demonstrate intent and prove technical feasibility through hands-on configuration.

Speaker Notes

Four shifts: Assess AI-Ability (don't force AI where deterministic rule wins), Own the Vibe (configure cost/latency/quality), Define the Failure State (design for AI failure), Prototype as Spec (the prompt IS the requirement).

The Anatomy of a High-Quality Prompt

Speaker Notes

Section transition.

Framework

The Anatomy of a High-Quality Prompt

Ambiguity creates inconsistency. Every prompt must explicitly define these four dimensions.
🎭
ROLE

Defines the model's expertise.

“Act as a senior B2B product researcher”
🎯
TASK

Defines the specific goal.

“Synthesise insights from raw feedback”
🚧
CONSTRAINTS

Defines the guardrails.

“Do not speculate. Use only the provided transcript.”
📐
FORMAT

Defines the output structure.

“Return a markdown table with headers.”

🦾 Model configuration — structure reduces randomness.

Speaker Notes

The four dimensions: Role, Task, Constraints, Format. Structure reduces randomness. Miss one of these and you're introducing inconsistency into your product. This is the framework learners will use in the Lovable lab next.

Prompting as Product Configuration

Speaker Notes

Section transition — the deepest section of the module.

Framework

Prompt Layers for Product Configuration

Three layers. Configure all three or you’re just wrapping a chat box.
🛠️
TOP LAYER
Tools and Functions

Shapes what the model can do, beyond text generation.

Example: [Calculator Tool], [CRM Search Tool], [API call]
💬
MIDDLE LAYER
User Prompts

Expresses intent based on dynamic, variable user input. The trigger for each system run.

Example: “Analyse this churn report for insights.”
⚙️
FOUNDATIONAL LAYER
System Messages

Defines global rules — persona, boundaries, safety protocols. The model’s “constitution.”

Example: “You are a Senior Data Analyst. Output only JSON.”

Speaker Notes

In Lab 1, you worked exclusively in the Middle Layer (User Prompts) inside Lovable's already-engineered system. To build YOUR product, you have to configure all three layers. System Messages are your real PRD — that's where you lock in the rules.

Core Techniques

The Prompting Strategy Matrix

As a PM, you’re choosing a configuration based on the problem. Three strategies. One trade-off triangle.
⚡
Rapid Ideation
Zero-Shot

Definition. Giving the AI a task with no examples, relying solely on your instructions.

Use case. Generate hypotheses, interview scripts, broad market summaries when you need volume over precision.

Example. “List 10 potential user problems for a new pet sitting app.”
📑
Output Consistency
Few-Shot

Definition. Providing 2–3 examples to guide strict structure or style.

Use case. Acceptance criteria, JSON schemas, status updates that must match team templates exactly.

Example. “Here are 3 examples of our user stories. Write a new story for the ‘Export PDF’ feature following this exact format.”
🧠
Complex Logic
Chain-of-Thought

Definition. Prompting the AI to explain its reasoning step-by-step before answering.

Use case. Sizing markets, analysing feedback, prioritisation. Forces the AI to “show its work.”

Example. “Think step-by-step. First, estimate the total addressable market (TAM). Then apply our segment filters to calculate the SAM.”

Speaker Notes

Three strategies: Zero-Shot (baseline), Few-Shot (the standardiser), Chain-of-Thought (the analyst). PMs choose based on the problem. Note we're going deeper on Few-Shot and CoT in the next two slides.

Few-Shot

Few-Shot Prompting

Instructions tell the model what to do. Examples show it how.
⚠️
Instruction Only
The Prompt
“Classify this user feedback as a Feature Request, Bug, or Praise: ‘The reports load slowly’”
The Result

“The reports load slowly” is a Bug.

The Failure

Without examples, the model guesses your criteria. It might call “Login is slow” a Bug, while you consider it a Feature Request for performance.

✅
Instruction + Data
The Prompt
“Classify this user feedback as a Feature Request, Bug, or Praise. Use these examples:
1. ‘Login is slow’ → Feature Request
2. ‘Login returns 404’ → Bug
3. ‘Love the login!’ → Praise
Input: ‘The reports load slowly.’”
The Result

The model matches “reports load slowly” to “Login is slow” and correctly tags it: Feature Request.

Zero-Shot is for creativity. Few-Shot is for compliance.

Speaker Notes

Walk through the comparison. Zero-Shot for creativity. Few-Shot for compliance. The 'Slow login → Feature Request' example matters because it shows how examples encode YOUR taxonomy, not the model's guess.

Chain-of-Thought

Chain-of-Thought (CoT) Prompting

Pattern matching isn’t enough for logic. You need reasoning.
⚠️
Prediction Only
The Prompt
“Is ‘Add AI Avatars’ a high priority feature? (Context: our Q3 goal is reducing churn.)”
The Result

“Priority: High. AI features are trending and usually drive user engagement.”

The Failure

The model relies on surface-level patterns. It sees “AI” (a popular topic) and predicts “High Priority”, ignoring your specific churn goal.

✅
Prediction + Reasoning
The Prompt
“Is ‘Add AI Avatars’ a high priority feature? Think step-by-step:
1. Define the primary driver of our churn.
2. Evaluate if ‘AI Avatars’ directly solves that driver.
3. Assign priority based only on that evaluation.”
The Result

“Step 1: Churn is primarily driven by high costs. Step 2: AI Avatars add value but do not reduce cost. Conclusion: Priority Low.”

Few-Shot for format. Chain-of-Thought for analysis, math, logic, priority.

Speaker Notes

Walk through the AI Avatars example. The model wants to call AI features 'High Priority' because it pattern-matches on 'AI = good'. CoT forces it to LINK the feature to the actual goal (churn) before deciding.

Hyperparameters

From Strategy to Spec: Model Configuration

Your prompt is the software. These settings are the operating environment.
🌡️
The Risk Slider
Temperature

Adjusts response randomness to control creativity or precision.

When. Low (0.2) → product logic, code, data. High (0.7+) → ideation, chat.

In the wild. Spotify uses low temp for support summaries (facts). Netflix high for title brainstorms (wild ideas).
🎯
The Quality Bar
Top P

Limits the model to only the top % of likely words to control vocabulary quality.

When. Cuts off “weird” or long-tail hallucinations without making outputs boring.

In the wild. Salesforce uses lower values for legal content. Netflix expands it for diverse storytelling.
💰
The Budget Knob
Max Tokens

Sets a hard limit on token output to control latency and cost.

When. Always set a limit. Prevents rambling, infinite loops, wasted API budget.

In the wild. Spotify forces concise summaries. Salesforce compresses CRM notes. Figma stops repetitive UI copy.

Pro tip. Don’t guess. Run a parameter sweep — test multiple settings, pick the one that aligns with your product goals.

Speaker Notes

Three knobs: Temperature (creativity slider), Top P (vocabulary filter), Max Tokens (cost ceiling). Real-world examples ground the trade-offs. Pro tip: always run a parameter sweep — don't guess.

Fine-Tuning

The Role of Fine-Tuning

Behaviour, not knowledge.
🧬
Behaviour, not knowledge

Fine-tuning bakes instructions directly into the model’s weights. Unlike Few-Shot, this eliminates the need to send long, expensive examples with every API call — reducing latency and cost.

GitHub Copilot. Not just “prompted” to write code. Fine-tuned on billions of lines to instinctively understand syntax, style, and logic patterns — without specific instructions.
⚠️
The Knowledge Misconception

Don’t use fine-tuning to teach the model your proprietary data or policies. Models are probabilistic engines, not databases — they cannot “look up” facts and will hallucinate when uncertain.

To stop hallucinations on data. You need Retrieval Augmented Generation (RAG). Coming up in Module 3.

Pro tip. Use fine-tuning to bake in skills, not facts.

Speaker Notes

Fine-tuning bakes BEHAVIOUR into weights — not knowledge. Use it for skills (style, format, code patterns), not for facts (prices, policies, specific data). For facts, you need RAG (Module 3).

Decision Framework

🔎 The Optimisation Decision Framework

Diagnose the problem to pick the right tool. PMs must triage — not say yes to “fine-tune it”.
1
Symptom
“The model gives inconsistent answers”
Tool
Few-Shot Prompting

If the model oscillates between good and bad outputs, it usually just needs clearer guardrails or examples. Fastest, cheapest fix.

2
Symptom
“The model doesn’t know our specific data”
Tool
RAG

If the user asks about “User X’s refund status”, the model can’t guess. It needs to read your database. No training will fix this.

3
Symptom
“The model sounds like a robot, not our brand”
Tool
Fine-Tuning

If content is correct but the vibe is wrong (too formal, wrong code syntax), retrain the model’s weights to mimic your voice or format.

Coming up. A deep technical dive on RAG in Module 3.

Speaker Notes

The triage framework. When stakeholders shout 'fine-tune the model!' your job is to diagnose. Inconsistency? Few-Shot. Missing data? RAG. Wrong vibe? Fine-Tuning. Saves your company $50k of unnecessary fine-tuning runs.

Workflow Shift

From PRDs to Prompts

Your prompt is the prototype. The interpretation gap between Product and Engineering closes.
📄
Old Way · Paper Spec
  • A static text document describing desired behaviour, like “the chatbot should be helpful and polite.”
  • PMs handed their requirements doc to Engineering to interpret it.
  • You wait 2 weeks and find “polite” means different things to you, Eng, and the model.
📦
New Way · Prompt Spec
  • A working system prompt using the four prompt anatomy configurations and prompting techniques.
  • PMs build the logic in a playground and test edge cases immediately.
  • You hand the working prompt to Eng and prove the logic works — no guessing required.

Speaker Notes

Old way: paper spec, hand off to Eng, wait, find out it doesn't work. New way: prompt spec, prove it in the playground, hand off a validated configuration. Closes the interpretation gap. Your prompt is the prototype is the requirement.
