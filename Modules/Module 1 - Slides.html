The AI-First Product Mindset

Every PM is now an AI PM

The PM role is bending around one technical fact.

Traditional PM assumptionWhat AI broke
Outputs are deterministicOutputs are probabilistic — drift, hallucination, variance
Spec is a docSpec is a doc + prompt + data corpus + eval set
UI is command-drivenUI is intent-driven and often invisible
Workflows are sequentialWorkflows are agentic — branched, conditional, handed off
Ship + monitor with analyticsShip + eval harness + human rubric + guardrails

Speaker Notes

This table is the spine of the entire course. Pin it. Each module reinforces one row.
Deterministic vs. non-deterministic

Why this is hard

Deterministic

Same input → same output. SQL, regex, every API you've ever shipped.

Specs assume the system behaves.

Non-deterministic

Same input → variable output. Every modern LLM, every agent.

Specs must shape behaviour and measure it.

Your job: narrow the variance. Configuration (prompts, RAG, fine-tune), guardrails, and evals are the levers.

Speaker Notes

Use a quick anecdote — same prompt, two different responses live in ChatGPT. Sells the variance point in 30 seconds.
The PM's dual role

Navigating uncertainty

  • Inward — translate non-determinism into product specs your team can build against (prompt, RAG, eval, guardrail).
  • Outward — translate non-determinism into user expectations the product can honour (trust UX, confidence cues, escape hatches).

You are the broker between probabilistic behaviour and human trust.

Speaker Notes

Both directions are PM work. Engineers will not own the user-trust side. Designers will not own the eval side. You do.

The Anatomy of a High-Quality Prompt

Five elements every production prompt declares

  1. Context — who the AI is, what system it lives in, what it knows.
  2. Task — the explicit instruction (verb-first).
  3. Constraints — must-not-do, format requirements, scope.
  4. Output format — schema, length, structure.
  5. Examples (few-shot, when useful) — 1–3 ideal pairs.

If any element is missing, your output will drift.

Speaker Notes

Prompting as Product Configuration

You are not chatting. You are configuring.

Once you treat the prompt as configuration, every framework becomes obvious.

TechniqueUse when
Zero-shotSimple instruction, model already knows the domain
Few-shotYou need a specific format or style — show 1–3 examples
Chain-of-thoughtMulti-step reasoning required
System prompt + rolePersona, persistent guardrails, organisation context

Speaker Notes

Tie each row to a Juno scenario. Few-shot for "draft a P0 spec." Chain-of-thought for "prioritize these 15 risks." System prompt for "be a risk watchdog, never the executor."
Hyperparameters

The two dials PMs should know

Temperature

0 = deterministic-ish (same prompt, same answer). 1+ = creative. Spec it for your job. Juno's risk watchdog persona = low. Juno's brainstorming mode = high.

Max tokens / response length

Cap it. Long outputs hide failures. Short outputs force prioritisation.

Top-p, frequency penalty, presence penalty — nice-to-have, not must-have for PM-side decisions.

Speaker Notes

The point is awareness, not mastery. PMs should know temperature exists and that it's a product decision.

Self-review checklist

Before you ship the system prompt

  • Does the persona name the role and the operating context?
  • Are scope boundaries explicit ("only act on Slack escalations tagged P0")?
  • At least 3 guardrails, including 1 refusal rule?
  • Output format declared (markdown, schema, length cap)?
  • An example included for the trickiest case?

Strategic limits of prompting

The Optimization Decision Framework

Three levers. Cheapest first.

LeverTry whenCost / time
PromptThe model already knows the domain. Behaviour needs tuning, not knowledge.Minutes. Almost free.
RAGYou need to ground the model in your data. (M3 lives here.)Days. Real infra cost.
Fine-tuneStyle/format/behaviour matters more than retrieval. Last resort.Weeks. Real infra + training cost.

If you can fix it with the prompt, do not build infra.

Speaker Notes

This sets up M3 (RAG) and previews fine-tuning, which we touch but don't deep-dive. PMs need to know the framework, not implement fine-tunes.
The Role of Fine-Tuning

Mostly: don't

  • Fine-tuning bakes behaviour into weights. Powerful, but inflexible.
  • Fine-tunes drift: base models update, your fine-tune doesn't.
  • Use when: format/tone/persistent behaviour at scale, and you have a thousand+ high-quality examples.
  • Do not use when: facts change weekly, you don't have an eval harness yet, or a system prompt + few-shot would work.

Speaker Notes

Most learners will never own a fine-tune. Make sure they know the decision criteria so they can push back when an engineer suggests it prematurely.
From PRDs to Prompts

The PM artifact is changing

In an AI-native team, the PRD is no longer the source of truth. The source of truth is:

  • The PRD (what & why)
  • The system prompt (how the AI behaves)
  • The data corpus + retrieval rules (what it knows) — M3
  • The eval set (how we know it's working) — M6

You will commit all four to your juno-pm/ repo by M6.
